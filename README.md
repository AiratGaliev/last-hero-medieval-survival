# Последний герой: Средневековое выживание (The Last Hero: Medieval Survival)

Bullet-heaven роглайт (клон Vampire Survivors) на **нативном Phaser 4** для
**Yandex Games**. Ассеты — [Tiny Swords](https://pixelfrog-assets.itch.io/tiny-swords)
от Pixel Frog.

Документация: [`docs/TZ.md`](docs/TZ.md) · [`docs/TILEMAP.md`](docs/TILEMAP.md) · [`docs/ROADMAP.md`](docs/ROADMAP.md) · [`worklog.md`](worklog.md)

---

## Что в игре

| | |
|---|---|
| Матч | 15 минут, финальный босс на 15-й минуте |
| Герои | 4 — Воин, Лучница, Копейщик, Монах |
| Сложности | 2 — «Поход» и «Кошмар» (×1.6 к счёту) |
| Оружие | 7, по 5 уровней + эволюция в 6-й |
| Пассивные | 9, по 5 уровней |
| Враги | 13 типов, включая элит, мидбосса и финального босса |
| Достижения | 12 |
| Лавка | 5 постоянных улучшений по 3 уровня |
| Рекорды | общий зал Яндекса (для авторизованных) + локальная таблица (10 строк) |

Эволюция оружия требует 5-го уровня ствола **и** пассивку-партнёра
(меч + мощь, лук + молниеносность, копьё + пир, молот + щит, бомба + удача,
аура + сердце, ножи + сапоги).

|---|---|

которым нужен собственный сервер.

## Ветки, Pull Request и CI — обязательные правила

Эти правила обязательны для каждого изменения. Не обходите процесс ради скорости:
он разделяет ежедневную разработку, приёмку кандидата и релиз.

### 1. Назначение постоянных веток

| Ветка | Назначение | Что в неё можно направлять |
|---|---|---|
| `main` | Стабильная версия и релиз Yandex Games | Только PR из `test`; исключение — аварийный `hotfix/*` по процедуре ниже |
| `test` | QA-кандидат на выпуск | Только PR из `dev` |
| `dev` | Общая интеграционная ветка | Только PR из рабочих веток |
| Рабочие ветки | Разработка отдельной задачи | Создаются от актуальной `dev`, затем направляются в `dev` |

**Запрещено:** прямой push в `main`, `test` и `dev`; PR из рабочей ветки прямо в `test`/ `main`; PR `dev → main`; PR `test → dev`. Не создавайте параллельные долгоживущие ветки без отдельного согласования. Быстрый CI автоматически проверяет допустимую пару source/base и завершится ошибкой при неверном маршруте PR.



### 2. Как создать ветку и начать задачу

1. Обновите локальную `dev` и создайте новую рабочую ветку от неё:
   ```bash
   git switch dev
   git pull --ff-only origin dev
   git switch -c feat/<короткое-название>
   ```
2. Допустимые префиксы: `feat/` / `feature/` — функциональность, `fix/` — исправление, `refactor/` — рефакторинг, `test/` — тесты, `docs/` — документация, `chore/` — инфраструктура. Для аварийного исправления от `main` используйте `hotfix/`; такую ветку разрешено направить в `main` и затем через PR вернуть в `dev`. Используйте короткое имя задачи латиницей, нижним регистром и через дефисы.
3. Работайте и коммитьте только в своей ветке. Не используйте `git push --force` для общих веток. Перед созданием PR убедитесь, что рабочее дерево не содержит чужих изменений.

Пример обычной задачи: `feat/enemy-telegraph` → PR в `dev`.

### 3. Допустимый маршрут PR

```text
feat/* | fix/* | refactor/* | test/* | docs/* | chore/*
                         │ PR + быстрый CI
                         ▼
                        dev
                         │ PR + быстрый CI + E2E
                         ▼
                        test
                         │ PR + быстрый CI + E2E
                         ▼
                        main → релизная сборка
```

- **Рабочая ветка → `dev`:** один PR на одну логически завершённую задачу. До слияния должен пройти быстрый CI. Браузерные E2E здесь автоматически не запускаются.
- **`dev` → `test`:** только когда сформирован цельный кандидат на приёмку. PR запускает быстрый CI и весь `npm run test:e2e` на Chromium для desktop и mobile. Не обходите и не подменяйте эти проверки.
- **`test` → `main`:** только после QA-приёмки кандидата. PR повторно запускает быстрый CI и E2E против итогового кандидата. После успешных проверок не добавляйте новые коммиты в кандидат — при любом изменении проверки должны пройти заново.
- Если E2E не прошёл, исправьте проблему в рабочей ветке, проведите PR в `dev`, затем обновите PR `dev → test` и повторите приёмку. Не исправляйте код прямыми коммитами в `test`.
- Аварийный `hotfix/<название>` создаётся **от `main`** и может направляться прямо в `main` только для восстановления production-критичного дефекта. Быстрый CI и E2E обязательны; после слияния изменение необходимо перенести обратно в `dev` и `test` через PR.

### 4. Что запускать локально

Установите зафиксированные зависимости командой `npm ci`. Перед PR рекомендуется выполнить:

```bash
npm run check
npm run build
```

| Проверка | Где запускается автоматически | Правило |
|---|---|---|
| `npm run check` | Каждый PR в `dev`, `test`, `main` | Обязательно: TypeScript + ESLint |
| `npm run build` | Каждый PR в `dev`, `test`, `main` | Обязательно: проверка production-компиляции |
| `npm run test:e2e` | Только PR в `test` и `main`; также вручную в Actions | Полная браузерная приёмка, не запускается для обычных PR в `dev` |
| `npm run test:e2e:ui` | Автоматически не запускается | Только интерактивная локальная отладка Playwright; не добавлять в обычный CI |
| `npm run build:yg` | Только релизный workflow на `main` | Создаёт и проверяет `release/tiny-sword-survivors.zip` |

Рабочие ветки не запускают CI на каждый push: быстрые проверки выполняются в PR. Не запускайте E2E вручную после каждого изменения и не включайте `test:e2e` / `test:e2e:ui` в быстрый workflow. Тесты следует писать и обновлять вместе с кодом, а запускать на этапе приёмки.

### 5. Обязательные требования к PR

Перед отправкой PR проверьте всё следующее:

- [ ] Базовая ветка верна: рабочая задача → `dev`, кандидат → `test`, релиз → `main`.
- [ ] PR решает одну понятную задачу; заголовок конкретен, описание сообщает причину и результат.
- [ ] В описание внесены выполненные проверки и честно перечислены проверки, которые не запускались.
- [ ] Для изменений геймплея/UI описаны затронутые сценарии; при необходимости приложены скриншоты/видео.
- [ ] Автоматические проверки требуемого этапа завершились успешно; ошибки не маскируются отключением тестов, таймаутов или lint.
- [ ] Документация и тесты обновлены, если поведение, требования или сценарии изменились.
- [ ] В PR нет секретов, локальных архивов релиза, лишних generated-файлов и несвязанных изменений.

Используйте шаблон PR в `.github/pull_request_template.md`. Не сливайте собственный PR до прохождения обязательных проверок.

### 6. Какие workflow существуют

- **CI Fast** (`.github/workflows/ci.yml`) — `npm ci`, `npm run check` и `npm run build` для PR в `dev`, `test`, `main`. Chromium не устанавливается, E2E не запускается.
- **E2E** (`.github/workflows/e2e.yml`) — Playwright для PR в `test` и `main`; при падении сохраняет диагностику Playwright.
- **Release** (`.github/workflows/release.yml`) — выполняет `npm run check` и `npm run build:yg` только на `main` и публикует ZIP как артефакт GitHub Actions. Ручной запуск разрешён только при выборе ветки `main`.

GitHub branch protection должна требовать статус `CI Fast / fast-checks` для всех трёх постоянных веток и `E2E / browser-e2e` для `test` и `main`; обязательны PR, запрет force-push и удаления постоянных веток. Назначьте правила защиты в **Settings → Rules → Rulesets** (либо **Settings → Branches**, если используется классическая защита). Одна документация не блокирует обход — настройки защиты должны быть включены в GitHub.

## Автоматические браузерные проверки

Playwright проверяет запуск игры на Chromium desktop и mobile, в русском и английском режимах, а также игровые регрессии. Локальный запуск делайте осознанно — преимущественно перед приёмкой, а не после каждого изменения.

```bash
npm ci
npx playwright install chromium
npm run test:e2e
```

`npm run test:e2e:ui` открывает интерактивный Playwright Test UI и предназначен для ручной отладки. Он не включён ни в один автоматический workflow. E2E запускается в CI для PR в `test` и `main`; PR в `dev` использует только быстрые проверки. При падении E2E workflow сохраняет trace, скриншоты и видео как артефакты.

### Таблица рекордов

Гибрид: **авторизованные** игроки попадают в общий зал площадки
(`ysdk.leaderboards`), **гости** видят локальную таблицу на устройстве.

Гостей SDK в общий зал не пускает — `setScore` доступен только авторизованным.
Поэтому локальная таблица нужна всегда, а заодно служит резервом, если запрос
к SDK не прошёл. Убийства/уровень/время едут в компактном `extraData`
(`kills|level|time|victory`), имя и счёт SDK отдаёт сам.

Техническое имя таблицы в консоли: **`tss_score`** (`LEADERBOARD_ID` в
`src/platform/player.ts`).

### Монетизация

- **Межстраничная** — после сохранения рекорда на экране результатов,
  с собственным кулдауном 150 с (у площадки свой лимит поверх).
- **Rewarded** — кнопка «ВОСКРЕСИТЬСЯ» на экране смерти, один раз за матч,
  не после победы. Воскрешение слабое: 40% HP, серия сбрасывается, 1.5 с
  неуязвимости — иначе бесплатные жизни ломали бы баланс.

### Авторизация

Вход предлагается **явной кнопкой** в главном меню (требование 1.2: не дёргать
окно входа без повода). Плашка вверху меню показывает состояние: гостю —
«ВОЙТИ В АККАУНТ ЯНДЕКС», авторизованному — имя из профиля.

Без входа общий зал рекордов недостижим: `leaderboards.setScore` доступен
только авторизованным, поэтому гости видят локальную таблицу.

### Что нужно сделать в консоли

1. Создать таблицу рекордов с техничным именем `tss_score` (сортировка по
   убыванию, тип `numeric`).
2. Включить облачные сохранения, если хотите прогресс между устройствами
   (для игр, залитых архивом, SDK сама делает `localStorage` надёжным).
3. Заполнить черновик: название, описание, «Как играть», категория, иконка,
   обложка, скриншоты, платформы, ориентация.
4. Загрузить `release/tiny-sword-survivors.zip`.

## Локализация

- `src/i18n/ru.ts` — эталонный словарь, из него выводится тип ключей.
- `src/i18n/en.ts` — тип импортирован у русского, поэтому **отсутствие
  ключа — ошибка компиляции**, а не строка на русском в английской версии.
- `t('ключ', { v: значение })` — подстановки в виде `{v}`.
- Словари грузятся динамическим `import`: в бандл попадает только активный.

Порядок важен: язык определяется **до** импорта игровых модулей
(см. `src/main.ts`) — иначе строки в `data.ts`, вычисляемые на этапе импорта,
зафиксировали бы русский язык.

Модерация проверяет все заявленные языки. После правок словаря обязательно
проверяйте оба: `?lang=ru` и `?lang=en`.

## Ассеты

Файлы лежат в `src/assets` и подключаются через `import.meta.glob`
(`src/game/assets.ts`), поэтому в `dist` попадают с хешем в имени — после
деплоя браузер тянет свежие спрайты. Vite также схлопывает одинаковые файлы:
663 исходника → 649 уникальных по содержимому.

`src/assets/tiny-swords` — импорт пака [Tiny Swords](https://pixelfrog-assets.itch.io/tiny-swords):
570 PNG, все имена приведены к правилам проекта (ASCII, нижний регистр,
kebab-case), служебные файлы Unity (`.meta`, `.anim`, `.controller`) и
справочник `Unity Tile Guide` не импортируются. Обновление пака — одна команда:

```
node scripts/sync-assets.mjs            # сухая сверка: что разошлось
node scripts/sync-assets.mjs --write    # копировать только различающиеся файлы
```

Скрипт сам строит карту «пак → проект» по правилам в начале файла, сверяет
SHA-256 и копирует байт в байт; совпадающие файлы не трогает, ничего не
удаляет, а на неизвестную папку в паке падает с ошибкой вместо молчаливого
импорта. Имена, которые kebab-case ломает (`bigbluebutton-regular.png`,
`lancer-downright-attack.png`), перечислены в `FILE_OVERRIDES` — на них ссылается
код, переименование сломало бы загрузку.

Сам пак дублирует картинки в нескольких местах (`Pawn and Resources/Pawn/*` =
`Units/*/Pawn/*`, `Gold Resource 2..7` = `Gold Stone 1..6`, `Bush 1..4` =
`Bushe1..4`). Копии в проект не тащатся: их отсекает `DEDUPE_DIRS` (сравнение
идёт по содержимому всего пака, а не по диску — результат не зависит от
порядка обхода и работает при импорте с нуля) и список `SKIP_FILES`.
Одинаковые картинки под разными именами, которые значат разное
(`Attack.png`/`Inven_Attack.png`, `arrow.png`, `heal-effect.png`), наоборот,
сохраняются все.

Phaser грузит только ключи из `BootScene.preload()` (97 файлов). `asset()`
бросает исключение, если файл переименован, — это лучше молчаливого
пустого спрайта.

Библиотека шире, чем используемая часть: из 570 PNG грузится 119
(`units/` — 60, `terrain/` — 38, `ui/` — 11, `buildings/` — 6,
`particle-fx/` — 4), а `enemies/` (123), `resources/` (30) и остатки `units/`
пока не задействованы — это материал для будущих врагов и базы. Хранить
стоит: Vite схлопывает одинаковые файлы по хешу, неиспользуемое просто лежит
на диске и браузером не качается.

Шрифт Pixelify Sans лежит в архиве: `fonts.googleapis.com` из России
недоступен, а это ~60% аудитории Yandex Games.

## Проверка архива

`npm run build:yg` останавливается с ненулевым кодом, если нарушено любое из
требований: `index.html` не в корне, в именах есть пробелы или кириллица,
размер больше 100 МБ, в `index.html` есть внешние ссылки, нет SDK или
осталась ссылка на Google Fonts.
